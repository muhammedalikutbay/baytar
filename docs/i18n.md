# Internationalization

Baytar supports Turkish, English, German, Spanish and French. The Turkish source dictionary defines the translation keys and placeholders.

`app/src/lib/i18n/tr.ts` exports `trSource` for tooling and `tr` for the active UI dictionary. Keep the existing `tr` import path in components. `TranslationKey` is derived from `trSource`; English is the fallback for each missing or empty translated value. Vite discovers named locale exports in `locales/*.ts` automatically, including translations merged later.

Startup selects `?lang=xx`, then `localStorage['baytar.locale']`, then the first supported primary subtag in `navigator.languages`, then English. A query selection is persisted. When localStorage is empty, startup restores the durable `ui_locale` setting before mounting the workspace and reloads if needed. Changing language stores both preferences and reloads because some labels are module constants. When localStorage is unavailable, a language query keeps reloads stable. The document language is set during locale initialization.

Currency and the default phone country load once before the workspace or print document mounts. Settings use `currency` and `phone_default_country`, with localStorage caches. Turkish defaults to TRY/TR; German, Spanish and French default to EUR and DE/ES/FR. English uses USD for a US browser, GBP for GB, otherwise EUR; its phone country uses the browser region or GB. Supported currencies have two minor-unit digits. Changing currency only changes display; it never converts stored amounts.

Use `intlLocale()` for displayed dates, numbers, region names and sorting. Calendars start on Monday in every locale. Keep Turkish-aware search folding unchanged. User-entered data, saved templates and built-in catalogue names are preserved. Reminder defaults and print labels come from the active dictionary. Reminder placeholder identifiers remain unchanged in all languages, including `{sahip}` and `{hasta}`.

CSV exports retain the existing UTF-8 BOM, semicolon separator, decimal comma and ISO dates for compatibility. The frontend supplies the ordered localized headers; Rust checks their column count and escapes them. Import report labels, count templates and issue descriptions also come from the dictionaries; original legacy values remain intact.

## Add a language in five steps

1. Add its code, native name and Intl locale to `locales` in `app/src/lib/i18n/index.ts`, and to the Rust `ui_locale` allowlist in `app/src-tauri/src/settings.rs`.
2. Create `app/src/lib/i18n/locales/<code>.ts`, exporting a plain named object (`export const xx = { ... };`). Copy every key from `trSource`. A type-only `TranslationKey` import with `satisfies Record<TranslationKey, string>` is optional.
3. Translate every value into natural UI language, keeping each `{placeholder}` exactly. Preserve newlines and any technical units. Do not translate saved clinical data or catalogue brand names.
4. Add sensible regional defaults in `region.svelte.ts`. Verify the native language choice, country names, money, Monday calendar, reminder defaults, print documents, CSV headers and saved import report using `?lang=<code>`.
5. Run parity, frontend checks and the production build. Update the supported-language feature lines in README. New dictionary keys must be added to Turkish and every locale in the same change.

## Verification

From `app/` (Node.js 24):

```powershell
node --test src/lib/i18n/parity.test.ts
node --test src/lib/i18n/*.test.ts src/lib/validation.test.ts src/lib/validation-time.test.ts src/lib/components/patients/clinical.test.ts src/lib/components/reminders/template.test.ts
npm.cmd run check
npm.cmd run build
```

Parity checks every locale file present, reporting missing and extra keys, empty or non-string values, and placeholder mismatches. German, Spanish and French use English until their dictionary files are merged; no registry edit is needed when they arrive. Translation workers must include the language/region, CSV and import-report keys added at the top of `trSource`.
